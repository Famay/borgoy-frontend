# Roadmap VerMeat

Документ фиксирует текущее состояние проекта, завершенные задачи и следующие шаги.

## Текущий статус

VerMeat находится в состоянии рабочего дипломного MVP.

Реализован полный пользовательский сценарий:

1. Поставщик регистрируется и входит в систему.
2. Для поставщика включается двухфакторный вход через email-код.
3. Поставщик создает партию боргойской баранины.
4. Поставщик загружает сертификат.
5. Backend рассчитывает SHA-256.
6. Сертификат загружается в Pinata/IPFS.
7. Хеш сертификата фиксируется в Polygon Amoy.
8. Система создает QR-код публичной проверки.
9. Покупатель проверяет продукцию без регистрации.
10. Администратор контролирует поставщиков, сертификаты, журнал аудита и состояние системы.

## План развития приложения после MVP

После защиты проект следует развивать не как набор отдельных экранов, а как сервис, готовый к пилотному использованию поставщиками. Основной принцип: сначала обеспечить сохранность и проверяемость данных, затем улучшать удобство работы и только после этого расширять бизнес-модель.

### Этап 1. Стабилизация MVP

Цель этапа: устранить риски, которые мешают безопасно использовать текущий функционал.

1. Сделать режим интеграций явным (выполнено):
   - добавить настройку `INTEGRATION_MODE=demo|live`;
   - запретить автоматический переход в demo-режим в production;
   - отображать режим работы IPFS и blockchain на странице состояния системы.
2. Добавить автоматическую очистку просроченных 2FA-кодов.
3. Добавить пагинацию и фильтры:
   - реестр сертификатов;
   - список партий (выполнено);
   - список поставщиков (выполнено).
4. Настроить обязательные проверки перед merge:
   - `npm run lint`;
   - `npm run build`;
   - `npm run server:typecheck`;
   - `npm run test:api`;
   - `npm run hardhat:test`.

Критерий завершения: сертификат нельзя бесследно удалить, production не может незаметно работать с demo-интеграциями, а основной пользовательский сценарий проверяется автоматически.

### Этап 2. Надежная пилотная эксплуатация

Цель этапа: убрать зависимость пользовательского запроса от скорости IPFS и Polygon Amoy.

1. Перевести обработку сертификата в фоновый процесс:
   - принимать файл и создавать запись со статусом обработки;
   - отдельно выполнять загрузку в IPFS;
   - отдельно отправлять blockchain-транзакцию;
   - повторять временно неуспешные операции;
   - сделать повторную обработку идемпотентной.
2. Расширить модель статусов сертификата:
   - `PENDING`;
   - `IPFS_UPLOADING`;
   - `BLOCKCHAIN_PENDING`;
   - `CONFIRMED`;
   - `FAILED`;
   - `CANCELLED`.
3. Улучшить эксплуатационную диагностику:
   - structured logs с `requestId`;
   - фактические health-check PostgreSQL, IPFS и blockchain RPC;
   - мониторинг ошибок API и фоновых задач;
   - уведомления при недоступности сервисов.
4. Настроить сохранность данных:
   - ежедневный backup PostgreSQL;
   - регламент хранения резервных копий;
   - документированное восстановление;
   - тест восстановления на отдельной базе.
5. Подготовить production-процесс:
   - отдельные `.env` для окружений;
   - ротация секретов;
   - checklist деплоя и отката;
   - smoke-тест после каждого деплоя.

Критерий завершения: временная недоступность IPFS или blockchain не приводит к потере сертификата, а администратор видит причину и состояние каждой незавершенной операции.

### Этап 3. Удобство работы поставщика

Цель этапа: сократить ручную работу при регулярной загрузке партий.

1. Добавить детальную страницу партии (выполнено):
   - основные сведения;
   - связанные сертификаты;
   - QR-код;
   - история публичных проверок;
   - история изменений.
2. Добавить экспорт QR-этикеток:
   - PNG для быстрого скачивания;
   - PDF для печати;
   - номер партии и сертификата;
   - короткая публичная ссылка.
3. Добавить массовый импорт партий:
   - шаблон CSV/XLSX;
   - предварительная проверка данных;
   - отчет об ошибках;
   - подтверждение перед сохранением.
4. Добавить поиск, сортировку и сохраненные фильтры для поставщика.
5. Добавить уведомления:
   - сертификат подтвержден;
   - обработка завершилась ошибкой;
   - сертификат аннулирован администратором.

Критерий завершения: поставщик может загрузить набор партий, распечатать QR-этикетки и самостоятельно понять состояние обработки без обращения к администратору.

### Этап 4. Прослеживаемость цепочки поставок

Цель этапа: перейти от проверки одного сертификата к истории движения продукции.

1. Добавить события жизненного цикла партии:
   - производство;
   - лабораторная проверка;
   - отгрузка;
   - приемка;
   - переработка или разделение партии;
   - продажа.
2. Хранить для события дату, организацию, место, ответственного пользователя и вложения.
3. Добавить роли и разграничение доступа:
   - `OPERATOR`;
   - `AUDITOR`;
   - `LABORATORY`;
   - текущие `SUPPLIER` и `ADMIN`.
4. Показывать покупателю публичную временную шкалу происхождения продукции.
5. Расширить smart contract только после фиксации бизнес-модели:
   - событие аннулирования сертификата;
   - при необходимости фиксация ключевых этапов движения партии;
   - версионирование контракта и сценарий миграции.

Критерий завершения: по QR-коду доступна понятная история происхождения продукции, а каждая организация изменяет только разрешенные ей данные.

### Этап 5. Интеграции и масштабирование

Цель этапа: подготовить сервис к подключению внешних участников и росту нагрузки.

1. Описать и версионировать API:
   - OpenAPI-спецификация;
   - API-ключи для внешних систем;
   - идемпотентные endpoint для импорта;
   - webhook-уведомления о смене статуса.
2. Подключать лаборатории и внешние реестры через отдельные адаптеры.
3. Провести нагрузочное тестирование:
   - публичная проверка по QR;
   - массовый импорт;
   - обработка очереди сертификатов.
4. Принять отдельное архитектурное решение по blockchain:
   - оставить публичную EVM-сеть;
   - перейти на production-сеть;
   - использовать permissioned-сеть;
   - хранить on-chain только минимально необходимые данные.
5. Подготовить политику хранения персональных данных, журналирования и доступа к документам.

Критерий завершения: внешняя система может безопасно передать данные и получить статус обработки, а выбранная blockchain-модель обоснована стоимостью, скоростью и требованиями к доступу.

## Критерии готовности дипломного MVP

Проект можно считать готовым к демонстрации, если:

- frontend открывается по HTTPS;
- API отвечает на `/api/health`;
- поставщик может войти с 2FA;
- поставщик может создать партию;
- поставщик может загрузить сертификат;
- сертификат получает SHA-256, IPFS CID и tx hash;
- QR-код открывает публичную проверку;
- покупатель видит результат проверки;
- администратор видит dashboard, поставщиков, реестр, журнал аудита и статус системы;
- документация актуальна.
